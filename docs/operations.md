# 数据口径与运行维护

## 数据流程

GitHub Trending（日/周）+ 按用途分配名额的 GitHub 搜索 → 按不可变仓库 ID 去重 → 元数据与 README → 规则/免费模型分类 → 人工覆盖 → 日快照 → 校验、构建 → 同一 Actions 流程部署 Pages。

每日最多更新 500 个仓库，GitHub 请求预算 850，搜索之间至少间隔 6.5 秒以兼容 Actions token 的搜索限流。候选按近期维护和关注量发现，Trending 优先加入。达到容量后为新候选预留名额，未更新的老项目仍保留原采集时间和目录记录。超时、限流不删除已有数据。

当前分类规则依据 Topics、简介和 README，关键词按英文词边界匹配，避免 video 命中 IDE、storage 命中 RAG。候选明确确认与 AI 相关后才出现在前端。分类不是对质量的背书，欢迎通过 overrides 校正。

## 真实增长

- 日快照按 UTC 日期去重，重复运行更新当日点，保留 90 天；不会为漏采日插值。
- 7 天差值：最新点与距离其 7 天前、允许 ±12 小时窗口的真实点做差。详情展示准确起止时间。
- 最新快照超过 48 小时不参与本站热榜；周榜来源的过期状态单独展示。
- 热榜门槛：AI 相关、未归档、可访问、最近 90 天有推送，周净增 ≥100，或净增 ≥30 且增长率 ≥10%。基数为零不计算百分比。
- 持续上升：在上述条件上，要求 8 个连续每日点、至少 5 个日间隔净增为正。
- GitHub 官方周榜保持独立口径和原始排序，未提供数字时显示缺失，不能替代本站净增。
- 大量取消 Star 导致负值会照实保留。仓库改名/转移按仓库 ID 延续历史，详情地址按当前名称生成。

## 失败恢复

1. 打开 Actions → Update radar and deploy Pages，查看失败的步骤；日志不输出密钥和原始模型异常内容。
2. GitHub API 403/429：遵守 Retry-After 和配额重置。过长等待结束本项抓取，保留旧记录；稍后手动重跑。
3. Trending 页面改版：解析不到项目会保留旧榜，更新时间不变。修复 `src/lib/trending.ts` 并更新测试 fixture，手动运行。
4. 模型不可用：采集和发布不受阻，维持规则标签及原始简介。配置有效免费 key 后手动运行可补齐。
5. 构建/校验失败：不会发布新站点，已上线版本继续可用。修正后重跑工作流。
6. 仓库 404/410：标记暂不可用，保留记录；普通网络或权限错误不当作删除。
7. GitHub 公共仓库长时间（60 天）无活动，定时工作流可能自动关闭。进入 Actions 点击 Enable workflow，并手动运行；正常每日快照提交会产生活动。
8. 并发更新由 workflow concurrency 排队；若人工推送导致自动提交冲突，该轮停止部署并可重跑，不使用强制推送。

## 定时验收

`cron: 23 0 * * *` 为北京时间每天 08:23。上线当天先验证 `workflow_dispatch` 完整采集和发布；首次自然 `schedule` 事件必须在预定时间后单独核验，不能把手动运行当作定时触发已验证。可运行：

```sh
gh run list --repo JavaArthur/ai-trend-radar --event schedule --limit 5
```

页面显示采集时间，浏览时超过 48 小时会提示过期。仓库 Actions 页面提供执行日志和失败记录，不额外引入付费监控服务。
